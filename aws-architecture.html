Zero Trust — Naming What's Already Built, Plus What's New

The platform already implements the individual controls Zero Trust requires — MFA on every human account (Deploy Guide Step 2), least-privilege IAM roles (ai-me-bank-app-role, scoped per-pilot), and encryption everywhere (KMS at rest, TLS 1.3 in transit) — but the site has never named Zero Trust as the organising principle tying them together. Doing so doesn't change any control; it gives the Board and Model Risk Committee a single, recognised framework name to audit against.

Never Trust, Always Verify

Every agent-to-service call is authenticated per-request via IAM — already true today, since ai-me-bank-app-role is scoped to specific S3 buckets and Secrets Manager paths, not broad access.

Least Privilege

No agent role has s3:* or iam:* — the existing ai-me-bank-app-role policy (Deploy Guide Step 3) already enumerates exact actions and exact ARNs.

Assume Breach

New in this page: network isolation (PrivateLink), detection tooling (GuardDuty/CloudTrail), and row-level data access control — assuming a credential or network segment could be compromised, and limiting blast radius accordingly.

How This Works — Vector Database & Retrieval, in Plain English

Several tabs on this page (especially Retrieval & Data Controls) assume you already know what a "vector database" or "embedding" is. Here's the actual mechanics, in order, using the Bank's real credit_policy_chunks table as the example — not a generic explanation.

Start with real documents.

The Bank's actual credit policy, RBI Master Directions, and KYC/AML guidelines — ordinary PDFs, nothing special yet.

Break each document into small pieces ("chunks").

A few paragraphs at a time — 400 tokens with 80-token overlap, per Deploy Guide Part 2 — not the whole document at once. This is why an agent can pull in one specific clause instead of an entire 200-page policy.

Convert each chunk into a list of numbers ("embedding").

An AI model reads each chunk and produces a fixed-length list of numbers that represents its meaning. Chunks about similar topics end up with similar numbers, even if they don't share a single word in common.

Store the chunks and their numbers together.

That's the "vector database" — in this case, ordinary PostgreSQL with the pgvector extension enabled, not a separate exotic system. The table is literally called credit_policy_chunks.

Turn the question into the same kind of number-list, and find the closest matches.

That's "retrieval." The agent then answers using only those retrieved chunks — not its own general knowledge — so answers stay grounded in the Bank's actual policy text, not an invented approximation of it. This is the "RAG" (Retrieval-Augmented Generation) pattern referenced throughout this site.

Gap closed: the existing VPC (ai-me-bank-vpc, 10.0.0.0/16, Deploy Guide Step 5) already separates public and private subnets, but every call from the agent platform to Claude currently leaves the VPC over the public AWS API endpoint. PrivateLink removes that public hop entirely.
In Plain English

Right now, when an agent asks Claude a question, that request leaves the Bank's private network, travels across the public internet (encrypted, but still public infrastructure), reaches AWS's public Bedrock endpoint, and comes back the same way. PrivateLink creates a dedicated, private tunnel that stays entirely inside AWS's own infrastructure — the request never touches the public internet at all, the same way a bank's ATM network doesn't route your PIN through the open internet even though the ATM itself sits on a public street.

Adding a Bedrock/Anthropic VPC Endpoint
AWS CLI — Extends Deploy Guide Step 5's VPC
# Private-subnet interface endpoint for Bedrock, same VPC as the EKS cluster
aws ec2 create-vpc-endpoint \
  --vpc-id $VPC_ID \
  --vpc-endpoint-type Interface \
  --service-name com.amazonaws.ap-south-1.bedrock-runtime \
  --subnet-ids $PRIV_A $PRIV_B \
  --security-group-ids $SG_BEDROCK_ENDPOINT \
  --private-dns-enabled \
  --profile ai-me-bank-staging \
  --tag-specifications 'ResourceType=vpc-endpoint,Tags=[{Key=Name,Value=ai-me-bank-bedrock-endpoint}]'
Script Breakdown
What it does: Calls the AWS EC2 API to provision a new "Interface Endpoint" inside the existing ai-me-bank-vpc, attached to the same 2 private subnets the EKS cluster already uses, and switches on private DNS so the normal Bedrock web address automatically resolves to this private address instead of the public one.
What it creates: One new AWS resource — a VPC Endpoint tagged ai-me-bank-bedrock-endpoint, visible in the AWS Console under VPC → Endpoints — plus a supporting security group ($SG_BEDROCK_ENDPOINT) controlling exactly which resources inside the VPC may use it.
Why it matters: Every one of the 3 pilots' Claude calls now travels entirely inside AWS's private backbone instead of the public internet, closing off an entire category of network-level interception risk — with zero code changes required in any agent.
✓ Once this endpoint exists, every agent — MSME's CAM Drafting Agent, Fraud's Recommendation Agent, Collections' Negotiation Agent — reaches Claude over the AWS private backbone, never the public internet, with no code change required (the SDK resolves the same API hostname to the private endpoint automatically).

Why Split Security and Logs Out of Prod
  • CloudTrail logs in a separate account survive even if the production account is ever compromised — an attacker with prod access cannot delete the evidence of what they did
  • GuardDuty findings are visible to the Security team without granting them standing access to production data or the credit/fraud/collections systems themselves

Gap closed: AI-GPolicy §16.3 already runs a real threat model — prompt injection, tool-chaining exploits, credential exposure through agent logs, delegation escalation. What's missing is mapping those same threats to a named, auditable methodology a Board or regulator recognises.
In Plain English

The Bank already has a list of things that could go wrong with its AI agents. Mapping to the recognised checklist matters because a regulator or auditor can check the Bank's list against the industry-standard one and see nothing was missed, rather than having to trust a home-grown list on faith.

That's not the actual framework name — MITRE ATT&CK is the general enterprise cyber-threat matrix; the AI/ML-specific counterpart is MITRE ATLAS (Adversarial Threat Landscape for AI Systems). Using the correct name matters if this ever goes in front of a technically literate Board member or auditor.

Gap closed: Langfuse (already built, Deploy Guide Step 20-ish, referenced throughout Helicopter View) traces every LLM call — prompt, tokens, latency, cost. That's the application layer. GuardDuty and CloudTrail are a different, complementary layer: AWS account and network activity, independent of what the agents themselves are doing.
In Plain English

Langfuse already records what each AI agent said and did. But it can't see if someone bypasses the agent entirely and queries the database directly through the AWS console. CloudTrail is the record of every action taken inside the AWS account, by anyone — human or machine. GuardDuty is a service that watches that record and flags anything that looks like an attack, the same way a bank's fraud system flags an unusual transaction pattern automatically rather than requiring someone to read every transaction by hand.

Three Layers, Not One

Langfuse (exists)

What did the agent say and do? Every prompt, tool call, and human decision — already live, feeds Governance → Audit Trail.

CloudTrail (new)

Who called which AWS API, when? Catches a credential being used somewhere Langfuse can't see — e.g. someone querying credit_policy_chunks directly via the RDS console, bypassing the agent entirely.

GuardDuty (new)

Is any of this anomalous? Cross-references CloudTrail, VPC Flow Logs, and DNS logs for known attack patterns — flags things neither Langfuse nor a human reviewing CloudTrail manually would catch.

Enable Both — Delegated to ai-me-bank-security (see Multi-Account tab)
# Organization-wide CloudTrail, logs land in ai-me-bank-logs account
aws cloudtrail create-trail --name ai-me-bank-org-trail \
  --s3-bucket-name ai-me-bank-cloudtrail-logs \
  --is-organization-trail --is-multi-region-trail \
  --profile ai-me-bank-security

# GuardDuty, delegated admin in the security account
aws guardduty create-detector --enable --profile ai-me-bank-security
aws guardduty create-members --detector-id $DETECTOR_ID \
  --account-details AccountId=$STAGING_ACCT,Email=... AccountId=$PROD_ACCT,Email=... \
  --profile ai-me-bank-security
Script Breakdown
What it does: Three API calls in sequence — creates one CloudTrail trail scoped to the whole AWS Organization rather than a single account, turns on GuardDuty in the security account, then explicitly registers the staging and prod accounts so that one GuardDuty instance watches both.
What it creates: A permanent, tamper-resistant activity log (ai-me-bank-org-trail) stored in the separate ai-me-bank-logs account, and one centrally-managed GuardDuty detector covering both staging and prod from the security account.
Why it matters: If prod is ever compromised, an attacker cannot delete or alter the evidence of what happened, because the logs live in an account they never had access to — and GuardDuty is already watching for the attack pattern before a human would notice it manually.
⚠ GuardDuty and CloudTrail findings should route to the same incident process already defined in AI-GPolicy §19, Incident Management — not a separate, parallel process the CISO's team has to remember to check.
Gap closed: today, credit_policy_chunks (Deploy Guide Part 2) has no row-level access control — any query against the table returns any chunk. That's fine at single-pilot scale with one policy corpus, but breaks down the moment Wave 2/3 introduces business-line-specific documents (Retail Lending, Treasury) that shouldn't all be retrievable by every agent.

Extending the Existing Table
Adds Access-Control Columns to credit_policy_chunks
ALTER TABLE credit_policy_chunks
  ADD COLUMN classification VARCHAR(20) NOT NULL DEFAULT 'internal',
  ADD COLUMN allowed_roles TEXT[] NOT NULL DEFAULT ARRAY['credit_officer'],
  ADD COLUMN business_line VARCHAR(50) NOT NULL DEFAULT 'msme';

-- Example: a Retail Lending policy chunk (Wave 2), not visible to MSME's agent
INSERT INTO credit_policy_chunks (chunk_text, source_ref, source_type, classification, allowed_roles, business_line, embedding)
VALUES ('...', 'retail_lending_policy_v3', 'internal_credit_policy', 'confidential',
        ARRAY['retail_credit_officer'], 'retail_lending', '...');
Script Breakdown
What it does: The ALTER TABLE adds 3 new columns to the existing credit_policy_chunks table with safe default values, so every row already in the table gets classified automatically — no manual re-tagging needed. The INSERT below it is a worked example, not a required step, showing how a future Retail Lending document would be labelled once Wave 2 adds it.
What it creates: Three new columns — classification, allowed_roles, business_line — on a table that already exists and is already in production use. No new table, no data migration, no downtime.
Why it matters: This is the one change that makes the vector database capable of safely holding more than one business line's documents. Without it, every future business line added to the shared platform would leak its policy documents to every other agent by default.
Retrieval-Time Filter — Applied in policy_qa()
SELECT chunk_text, source_ref FROM credit_policy_chunks
WHERE business_line = %(requesting_agent_business_line)s
  AND %(requesting_agent_role)s = ANY(allowed_roles)
ORDER BY embedding <=> %(query_embedding)s
LIMIT 5;
Script Breakdown
What it does: Adds two WHERE conditions to the query policy_qa() already runs (Step 5 in "How This Works" on the Overview tab) — before ranking chunks by similarity, it first narrows the search to rows matching the requesting agent's business line and role.
What it creates: Nothing new — this changes the shape of an existing query. The document-matching logic itself is untouched; it's now searching a smaller, permitted subset of the table instead of the whole thing.
Why it matters: Access control enforced at the database layer can't be forgotten by a future engineer adding a new agent — every retrieval automatically respects it, the same way a bank's core system won't let a teller pull up an account outside their permissions, regardless of what the teller's own front-end software does.
✓ Same pattern the reference document describes as "a UK employee cannot retrieve US-only documents" — here it's "the MSME agent cannot retrieve Retail Lending's confidential policy chunks," enforced at query time, not by trusting the agent to self-filter.

Not a Wave-1 blocker — with only MSME's policy corpus in the table today, every chunk is already effectively business_line = 'msme'. This becomes load-bearing exactly when Wave 2 introduces a second business line's documents into the same database.

PCI DSS — Relevant to Fraud Detection Specifically

Fraud Detection's Device/IP & Network Agent and Merchant/Beneficiary & AML Agent touch card/UPI/IMPS transaction data directly. AI-Readiness flags PCI DSS as relevant in passing; it isn't mapped clause-by-clause the way RBI/DPDP are on Compliance today. That mapping exercise is real work, not something to fabricate here — flagging it as an open item for Legal/Compliance to scope.

ISO/IEC 27001 — Distinct from the Existing ISO 42001 Target

AI-GPolicy targets ISO/IEC 42001 (AI Management System) by Year 3 on the AI Roadmap. ISO/IEC 27001 is a different standard — general information security management, covering exactly the controls in this page (network isolation, access control, incident management) rather than AI-specific governance. Both are relevant; neither is a substitute for the other.

Gap closed: RDS is already Multi-AZ (Deploy Guide Part 2) — that protects against a single Availability Zone failure. It does not protect against a full ap-south-1 region outage, and no RTO/RPO target has ever been stated for this platform.
In Plain English

Multi-AZ (already built) protects against one data centre in Mumbai having a problem — the backup copy is a few kilometres away, in a different building. Cross-region DR protects against a problem affecting all of Mumbai at once — the backup is in an entirely different city. RTO is how long it takes to get back up and running; RPO is how much data, in the worst case, could be lost in the gap between the last backup and the outage.

Cross-Region Failover — What Would Need to Change
  • RDS: enable cross-region automated backups to ap-south-2 (Hyderabad) or ap-southeast-1 (Singapore) if a second India region isn't available at build time
  • S3 (ai-me-bank-cam-docs): enable Cross-Region Replication to the same secondary region
  • EKS: a warm-standby cluster in the secondary region, scaled to zero until failover — not a duplicate always-on cluster, to control cost
  • DNS: Route 53 health-check-based failover routing, so a region outage redirects traffic without a manual DNS change under pressure
💡 Sequencing note, consistent with the Multi-Account tab: this is enterprise-scale resilience investment appropriate for Wave 2/3, not a Wave-1 blocker. Ship the 3 pilots on Multi-AZ first; add cross-region DR once the platform is running multiple business lines and an outage's blast radius is bank-wide, not one pilot.
