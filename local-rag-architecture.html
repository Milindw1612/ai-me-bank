Reading the Diagram — Notes

The flow, in brief

  1. Where the data comes from. The Loan lane starts fresh — an applicant fills out a form, there's no pre-existing record. The Fraud lane starts from an actual transaction databaseFRAUD — 10,000 records, sitting in a local JSON file today (simulating a Google Sheet), but in a real deployment this is a proper SQL/PostgreSQL/Oracle table. The architecture doesn't change either way — only where the rows physically live.
  2. Input captured. The Loan GUI collects the applicant's raw fields, including identifying ones (name, PAN, Aadhaar). The Fraud GUI just selects an existing row from the database, e.g. TXN-004521.
  3. Input Guard — the critical safety step.SHARED Before anything else runs, identifying data is removed. On Loan, name/PAN/Aadhaar are simply dropped — only cibil, income, requested amount, tenure continue forward. On Fraud, the real account_id is swapped for a reference token (ACC001247 → REF-88291) — the real ID never travels past this point.
  4. Router. A simple check decides which policy collection applies — loan_policies or fraud_policies. Nothing clever here, just which GUI the request came from.
  5. Hybrid RAG.SHARED The system builds a search query out of the numbers/signals already known (not out of any PII), and retrieves the actual policy clauses that apply — e.g. Loan retrieves LOAN-001 clause 4 (CIBIL threshold); Fraud retrieves FRAUD-001 clause 1 (velocity) and FRAUD-003 clause 2 (auto-freeze threshold). This is real hybrid dense+sparse search, not a keyword lookup.
  6. Deterministic Engine — this is what actually decides.SHARED Plain Python, no LLM involved. Loan: if cibil < 650 → Not Eligible. Fraud: signal scores sum to a risk score, compared against a flag threshold. The LLM downstream is never allowed to change this verdict — only explain it.
  7. Prompt Assembly — the merge point. This is where the verdict/score, the reasons, and the retrieved clause text all get combined into one prompt for the LLM. Nothing identifying is in this prompt — Loan's prompt never had PII to begin with (step 3 dropped it); Fraud's prompt carries the reference token REF-88291, never the real account ID.
  8. Gemini 3.5 Flash. Given that merged, PII-free prompt, the model's only job is to explain the already-made decision in plain language, citing the actual clause numbers. It is explicitly instructed not to change the verdict.
  9. Output, Watchdog-checked, then de-tokenized. Before the response leaves the server, the Watchdog re-checks the outgoing prompt for anything the Input Guard missed, checks the retrieval was actually confident, and checks the LLM's explanation didn't quietly contradict the verdict. Only then does REF-88291 get swapped back to the real account reference for the analyst's screen.
  10. Human-in-the-loop. Every result is labeled a draft. The Credit Officer or Fraud Analyst makes the real call — the system never auto-approves a loan or auto-confirms fraud on its own.
